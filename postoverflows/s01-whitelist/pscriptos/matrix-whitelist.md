## Matrix/Synapse whitelist

Postoverflow whitelist for known false positives caused by legitimate Matrix/Synapse traffic.

It does **not** whitelist Matrix traffic in general. An overflow is only discarded when it was raised by one of the scenarios below **and all** of its events match a known harmless request (method, status and exact path). As soon as a single other request is part of the overflow (e.g. `GET /_matrix/.env`), the alert is raised as usual. All other scenarios keep seeing Matrix traffic.

### `crowdsecurity/http-probing`

Only `GET` requests answered with `404`:

| Path | Reason |
| --- | --- |
| `/_matrix/client/(r0\|v3)/rooms/{roomId}/state/m.room.encryption` | Clients check every room for its encryption state. Unencrypted rooms answer with `404` (spec behaviour). |
| `/_matrix/federation/v1/event/{eventId}` | Remote homeservers fetch events that are unknown to this server. |

Since every room or event ID is a distinct path, a client opening a few rooms or a federating homeserver catching up easily exceeds the bucket capacity.

### `crowdsecurity/http-crawl-non_statics`

Only `GET` requests answered with `200` or `304`:

| Path | Reason |
| --- | --- |
| `/_matrix/client/v1/media/thumbnail/{serverName}/{mediaId}` | Clients load avatars and previews of a room in a burst. Thumbnails have no file extension and are therefore not detected as static resources. |

### Not whitelisted on purpose

- `/_matrix/client/*/login` and any other authentication endpoint
- `/_synapse/` (Synapse admin API)
- non-`GET` requests
- `403` responses: they are often generated by a reverse proxy or bouncer middleware and not by Synapse itself
